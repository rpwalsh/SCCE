## Defect 1 -- the summary that stands in for an answer never read the request

Measured on `reference:athens-country`, every step from the same turn of the baseline trace:

    local_evidence.plan.rank   ranked  "'Athens' is the capital and largest city of Greece."  FIRST, under `predicating`
    mouth.candidate.select     semanticCoreFactObject = "Athens is the capital and largest city of Greece"
    mouth.deterministic.select rows[0] head "'Athens' is the capital and largest city of Greece."
                               admissible: true   repeatsPrompt: false   covers: FALSE   -> rejected
    mouth.generate             surfaceRealizationId "candidate:deterministic:continuation-required"  (= empty text)
    mouth.source_summary_fallback  spoke "The Athens Metro runs three metro lines..."

Retrieval was right, ranking was right, and the core fact was right. `coversRequest` then rejected the answering
sentence because `mouthCoverageUnits` is `["athens","capital","which","country"]` and no correct answer to
"...the capital of which country?" can restate either "which" or "country" -- the interrogative, and the category
the answer replaces with "Greece". `selectedText` went empty and the turn fell through to the summary lane.

**The defect I fixed is not the rejection. It is what happened next.** `summarizeAdmittedSource` chose by
extractive salience and never saw the request at all, so the lane that speaks when everything narrower has failed
spoke a paragraph carrying ZERO of the asked relation, having just rejected one carrying it. A fallback that
settles strictly less of the request than a surface an earlier lane refused is not a fallback, it is a downgrade.

### The fix

`packages/kernel/src/source-summary.ts`. `centralSentences`/`summarizeSource`/`summarizeAdmittedSource` take an
optional `relationUnits`. Every sentence gets an `askedRelation` weight:

    askedRelation(s) = sum over asked-relation units u present in s of  log( N / sentenceFrequency(u) )

N is the number of sentences of this source, `sentenceFrequency` is the index the summarizer already builds for
its own similarity weights. Sentences order by `askedRelation` first and centrality second, and a sentence that
settles the relation is considered even where the Otsu centrality filter had dropped it.

The single call site (`production-turn-runtime.ts`, inside the existing source-summary block) passes
`requestRelationBeyondSourceIdentity(input.text, identityBound[0]!, corpusFunctionSymbols())` -- L1's definition
of the obligation, imported rather than re-derived, per the seam we agreed.

**Why inverse SENTENCE frequency and not a count.** This is the whole reason the fix needs no notion of a
question word. A unit the source states in every sentence scores exactly `log(1) = 0` and can order nothing; a
unit the source never states scores 0 for everyone. So the interrogative "which", which leaked into the unit
list because the live closed class held only 29 words, is inert here by construction -- I never had to decide it
was an interrogative. Same for "country": absent from every sentence, worth 0 to every sentence. What actually
orders Athens is "capital", which that article states in few sentences. This is `D = 0` from
`proof-addressed-memory.md` computed on the source's own statistics: score what distinguishes the candidates,
not what resembles the request.

Silent by construction, all three cases covered by regression tests that I verified fail with the ordering term
removed and pass with it (`packages/kernel/src/__tests__/source-summary.test.ts`):

- no `relationUnits` -> byte-identical summary
- relation units the source never states -> byte-identical summary
- a relation unit the source states in EVERY sentence -> byte-identical summary

No constant was added. No calibration id was needed: the ordering is a comparison, not a threshold.

## Defect 2 -- a date answer was read in the order the regexes ran, not the order the source wrote

`reference:academy-first-year` answered "11:00" to "In what year was the first Academy Awards ceremony held?".
The value arrives as `semanticCoreFactObject` with `contractSource: temporal_value`, from
`extractTemporalAnswerFromEvidence` (`semantic-obligations.ts`), whose result overrides every other answer at
`production-turn-runtime.ts` (`const proofAnswer = temporalAnswerValue || answerSurface.answer`).

The cause is not selection policy, it is extraction order. `extractSemanticItems` applies its clock-time pattern
(`\d{1,2}:\d{2}`) in a loop that runs BEFORE its written-date pattern, and both `add` into one array that the
caller then reads positionally with `items[0]`. So every clock time in a span sorts ahead of every date in it,
however far down the span it sits. In that span, measured off the trace's own sentence indices:

    sentence 11  "The first Academy Awards presentation was held on May 16, 1929 at a private dinner..."
    sentence 17  "...the results were given to newspapers for publication at 11:00 pm on the night of the awards."

`items[0]` was sentence 17's clock time. The function's own comments read this list positionally throughout --
"the opening block first, it carries the subject's own dates", and `items[1]` for the later of a lead's two dates
-- so the position it reads has to be the source's. One `.sort()` on the byteRange the extractor already records.

Regression test `packages/kernel/src/__tests__/temporal-answer-order.test.ts`, verified failing without the sort
with exactly the live symptom (`expected '11:00' to be 'May 16, 1929'`).

## What I proved false

- **"Ten of the twenty-one wrong rows are `singleCoreFact` over `selectedFacts`."** Two are. The ten are
  `mouth.source_summary_fallback`. The counts are in the table above and come from the baseline run's own trace.
- **"This is the mouth discarding the correct fact."** For the ten it is the mouth discarding the correct fact
  and then a *different* lane speaking, with a weaker requirement than the one that just rejected it. Fixing the
  discard alone would not have changed the answer, because the discard happens in a lane whose output was
  already empty.
- **"The `11:00` row is a value-type mismatch that needs the relation's observed value distribution."** It needed
  no distribution at all. It was array order. A clock time never outranked a date on merit; it outranked it
  because a `for` loop over one regex ran before a `for` loop over another.
- **"`revwar-end` is the same defect as `academy-first-year`."** It is not, and I did not fix it. Both dates sit
  inside one parenthetical of one sentence, so document order cannot separate them; deciding which endpoint of an
  attested interval "end" asks for needs the relation unit "end", and the mouth's coverage units for that turn
  are `["what","year","american","revolutionary"]` -- "war" and "end" were erased as request scaffolding before
  any gate saw them. That is upstream of me and L1 has it.
