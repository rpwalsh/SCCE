## Job 1 -- the relation backfill

### What the tool actually does, read before running it

`tools/accumulate-relation-observations.mjs` re-projects each stored source version through
`createTypedIngestProjector` and writes `relation_observations` rows. It writes **nothing else**: no graph node,
no graph edge, no hyperedge, no evidence span. Idempotent by construction -- the table's primary key is
`(relation_seed_id, channel, source_family_id, signature)` and the insert is `ON CONFLICT DO NOTHING`. Verified,
not assumed: the smoke run over 128 versions wrote 2,661 rows and an immediate re-run wrote 0.

Three things were wrong with it before it could be run corpus-wide, all now fixed in the committed tool:

1. **It held ONE transaction over the whole corpus.** `begin`, a row-at-a-time insert loop over every observation,
   `commit`. At corpus scale that is a write transaction open for tens of minutes while four lanes measure against
   the same server. It now sweeps by `source_version_id` keyset with one short transaction per batch of 64
   versions, multi-row inserts inside it, and a resume file so a failure costs one batch.
2. **It loaded every blob at once.** `select ... b.content ... limit 4000` buffers the whole result in the client;
   corpus-wide that is ~330 MB of blob text in one array before any work starts.
3. **One `evidence_spans` query per version** -- 24,735 round trips against the largest table in the schema. Now
   one `= any($1::text[])` query per batch.

### The finding the backfill surfaced: an identifier that enumerates instead of identifying

The first corpus-wide run died at version 768 with

    index row size 3112 exceeds btree version 4 maximum 2704 for index "relation_observations_pkey"

That is not a tuning problem. `relation-promotion.ts:480`:

    if (dependencyGroups.length > 1) return `dependency_set:${canonicalStringify(dependencyGroups)}`;

`sourceFamilyId` is the quantity promotion counts to decide whether a relation is corroborated by INDEPENDENT
sources, and for a source with more than one dependency group it is the entire sorted dependency list serialized
inline. Measured on one such source: `relationSeedId` 45 bytes, `channel` 17, `signature` 203, **`sourceFamilyId`
2,828**. Consequences, in order of seriousness:

- an identifier that enumerates its members is not an identifier: two sources over the same dependency set in a
  different order are different families, and one family cannot be compared against another without string
  compare over kilobytes;
- PostgreSQL refuses to index it past 2,704 bytes, so those observations cannot be stored at all.

Live counts: **13,950 stored rows over 70 families carry a `dependency_set:` id** (longest 2,384 bytes, just under
the limit); 485,552 rows over 19,600 families carry an ordinary single-group id (longest 55 bytes). All of the
`dependency_set:` ones come from the `corpus:source.5ab6...` construction-training aggregates.

**I did not change it, deliberately.** The fix is one line -- hash the sorted dependency set to a fixed-width id --
but it re-keys those 70 families, so until the 13,950 stored rows are re-derived the same family would be counted
under two ids and promotion would read one source's corroboration as two. Inflating independence is worse than the
unindexable key. The correct sequence is: change `sourceFamilyFor` to a digest, re-derive the affected rows, then
re-run the sweep. Re-deriving means clearing those 13,950 derived rows, which I was told to write up rather than
do. This is the write-up.

Meanwhile the sweep counts and reports every refusal rather than dying on it (`oversize signatures refused by the
index`), so the number is visible instead of fatal.

### The dominant relation: a real measurement, and it is not what it looked like

`graph_edges` holds 4,001,404 rows over **52 distinct `relation_id`**, and one id carries **1,810,867 of them
(45.3%)**. That is the "2 million edges being one relation" the earlier investigation flagged. It is neither a
genuine relation nor an ingestion artifact being promoted. It is an inverted index written as edges.

    relation_id 14e605ea...  n 1,810,867
      metadata  {"feature":"bi:!|100","relation":"mentions","forceClass":"learned_concept_prior","sourceSystem":"wikipedia"}
      source    evidence-chunk node, preview "'Amsterdam' ( ; ) is the capital and largest city of the Netherlands..."
      target    symbol node, representation {"feature":"bi:!|100"}

`graphbuild.ts:82` writes one `mentions` edge per (evidence span, feature) pair for up to 84 `sym:`/`bi:` features
per span. 81,005 spans times its mean fan-out is the 2,280,412 `mentions` edges that exist (1,810,867 tagged
`sourceSystem: wikipedia`, 469,545 untagged). And `relation_id` is a hash of the relation NAME, not of a predicate
instance, so **every `mentions` edge necessarily shares one id**. A 45% concentration over 52 ids is definitional,
not pathological, and deleting those rows would delete the feature index.

The number worth alarm is the other one. By relation label:

    mentions                       2,280,412   57.0%   evidence chunk -> symbol/bigram feature
    (no label, no forceClass)      1,528,513   38.2%   38 relation ids, imported and structural
    (no label, wikipedia prior)       94,037    2.3%
    states                            30,183    0.75%  <- the propositions. The whole semantic channel.
    contains                          29,179
    written-in                        25,866
    next-evidence                      6,366
    has-script                         4,645
    section-contains                   2,203
                                   ---------
                                   4,001,404   every edge accounted for

`states` edges carry the atoms `atomizeText` derives per span, capped at `MAX_PROPOSITIONS_PER_SPAN = 24`. There
are 30,183 of them over 81,005 spans: **0.37 propositions per span against a ceiling of 24.** Propositions are
0.75% of the graph; the feature index alone is 57%.

### What the backfill can and cannot buy -- read this before attributing anything to it

Promoted relations become graph nodes ONLY at ingestion time. `typed-ingest.ts:893`:

    const promoted = promotion?.promoted === true || sourceDeclaredZeroArity;
    if (!promoted) continue;

and the graph write in `ingestion-runtime.ts` runs inside the same ingestion pass. The backfill writes
`relation_observations` and nothing else, so **it changes what a FUTURE ingestion would promote and changes
nothing a turn can read today.** Corpus-wide today:

    promoted relation graph nodes        33,532
      anchor_derived                     33,213   (29,474 wiki links + 3,739 headings)
      weak_free_surface (prose)             318
      source_declared_structured              1

318 prose relations for the whole corpus. Recovering the rest needs a SECOND pass that re-projects each source and
writes the promoted relation graph for the seeds the accumulated observations now promote. The projection is
deterministic (fixed clock, fixed id namespace), so a second pass is well defined; it is roughly the same cost as
the first. It is not built. Anyone attributing a retrieval change to this backfill before that second pass exists
is attributing it to something that cannot have caused it.

### The fix, and the measurement that chose its granularity

`packages/kernel/src/structural-residue.ts`. Two language-free quantities over a token stream (word runs
lowercased, digit runs one token, every other non-space character its own token):

    symbolDensity     punctuation tokens / all tokens
    bigramDiversity   distinct token bigrams / bigram positions
    score             symbolDensity * (1 - bigramDiversity)

A key-value table is dense in symbols AND spends its length re-using one bigram skeleton. Prose is neither. No
casing, no suffix, no word list, no position, no language -- the test covers a Korean sentence and a Latin one.

The cut is **derived, not set**: Otsu's split of the corpus's own distribution of this score over all 1,918,749
sentences of all 73,480 promoted evidence spans = **0.1296**, putting 6.06% of corpus sentences above it.
`tools/derive-structural-residue-cut.mjs` recomputes it on any corpus; a 900k-sentence prefix of the same corpus
gives 0.1289, inside the id's own 0.005 resolution. Declared as `evidence.structural_residue_cut` in
`public-calibrations.ts` with its search entry, because a number nobody can find cannot be refitted.

**Sentence granularity, and that was measured, not assumed.** Scored on whole SPANS the statistic has real false
positives: `moldova national football team results (2020-present)` scores 0.647 on its span, and that span opens
with ordinary prose and merely contains a results table later. So the gate is applied to the surface that would be
spoken, never to the span:

    local-evidence-runtime.ts  both sentence rankers, alongside isHeadingOnlySurface
    mouth.ts                   the deterministic surface selection, refused rather than deprioritized

Refused, not deprioritized, on purpose. The existing comment there says markup surfaces "sort behind every surface
that is not, so it is still available when nothing else can be said" -- and tungsten is exactly the case where
nothing else can be said, so sorting cannot help. A turn holding nothing but apparatus has nothing to say, and
declining is the answer.

### The other half of Job 2, and what I proved FALSE about it

Book front matter is a different residue class and the structural measure does **not** catch it, which I measured
rather than assumed:

    book:harker      "The Project Gutenberg eBook of Dracula This eBook is for the use of anyone..."  score 0.058
    book:hispaniola  "NARRATIVE CONTINUED BY THE DOCTOR: HOW THE SHIP WAS ABANDONED . ..."            score 0.058

Both read as prose to any shape statistic, because they ARE prose. The criterion that should catch them is the
other half of the objective -- recurs across unrelated source families and explains no graph structure. I built it
and it did not separate. Reporting the negative:

- index: every sentence of every promoted span, whitespace-collapsed, word-normalized, counted by distinct source
  family. 73,480 spans -> 1,907,475 sentences -> 824,712 distinct forms.
- the top of that index is exactly right: `==References==` in 5,721 families, the repository's own licence banner
  (`Copyright (c) 2026 ... All rights reserved.` / `No license granted except by separate written agreement.`) in
  1,608 families, `==References== ==External links== *` in 1,305. The criterion finds real boilerplate.
- combined with "yields no prose relation" (`proseRelationMetadata` per sentence, pure), the conjunction flags 6 of
  266 baseline answers -- **1 of them correct, and NEITHER of the two it was built for.**

Two reasons, both mine, both measured:

1. **`source_title` is not a source family.** Every one of the 15 novels is ingested TWICE -- 2 distinct
   `source_id` and 2 `source_version_id` per title (dracula 2/2, moby dick 2/2, treasure island 2/2, ... , and 15
   more gutenberg sources carry an EMPTY `source_title`). So every Dracula-only sentence already scores
   "2 families" and the signal is swamped. A duplicate-ingest defect in its own right, and it matters to anyone
   counting independent sources over books.
2. The recorded baseline answers are whitespace-joined and clipped at ~300 characters, so the answer's sentences
   do not match the indexed sentence forms. `book:harker`'s recurring sentence ("You may copy it, give it away or
   re-use it under the terms of the Project Gutenberg License...") is the one that was clipped off.

So the recurrence criterion is **not falsified -- it is unmeasured**, and it needs a real family id plus live
answers rather than recorded ones. I did not ship a gate for it. Shipping an unvalidated gate over an index of
824,712 sentence hashes, on a measurement I already know is confounded, is how correct answers get deleted.

### "Stop ingesting it" -- not done, and why

The same pure predicate is now available to ingestion, and the natural rule is safe by construction: refuse to
promote a span whose EVERY sentence is residue (a span with a prose lead keeps its lead). But `status: "promoted"`
is written from nine separate places across the ingestion lanes (`wikipedia-v3-ingestor.ts:1629`,
`language-corpus-trainer.ts:126` and `:416`, `engineering-corpus-folder.ts:1368`, `scce2-to-v3-importer.ts:1392`,
`learned-code-proposer.ts:68`, `scce-runtime.ts:1679`, `learning-loop.ts:1090`, `workspace-core-fusion.ts:979`),
and verifying an ingestion-side change means re-ingesting an article, which needs a server restart. A worker does
not restart the shared server. Left for the integrator, with the predicate in hand.
