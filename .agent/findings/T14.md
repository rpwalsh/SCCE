# T14 — the 67 modules unreachable from the turn runtime

Method: importer map over every `.ts/.mjs` in the repo (not just the kernel), then production call-site proof in
`packages/server/src` and `packages/adapters-node/src` excluding tests. Classification rule used, stated so the
counts are interpretable:

- **B** = a real caller exists on a *live request* path that the import walk could not see (either the walk's entry
  point was below the real entry, or the caller is a route handler / adapter lane rather than `production-turn-runtime`).
- **C** = offline by purpose (ingest, training, evaluation, CLI, schema contract), even when an HTTP route can
  trigger that job. Reaching it from a turn would be wrong.
- **A** = cognition the turn ought to use, with no live-turn caller.
- **D** = no caller anywhere.

## Three flaws in the reachability measurement

1. **The entry point is one level too low.** `kernel.turn()` is `kernel.ts:649`, and it delegates to
   `productionTurnRuntime.turn(input)` at line 650. The delegation itself is clean — nothing else in `kernel.ts`
   runs inside a turn — but `kernel.ts` and `index.ts` are therefore *above* the entry, not unreachable, and the
   list reports the turn's own entry point as unreachable from the turn.
2. **The live turn is bigger than `kernel.turn()`.** `packages/server/src/routes.ts:810` calls
   `buildTurnDialogueBridge` and `:724` calls `latestDialogueStyleProfile` on the chat request path, and
   `packages/adapters-node/src/workspace-runtime.ts` runs a second answering lane
   (`createWorkspaceCoreFusion:324`, `answerFromWorkspaceCoreContext:572`, `planStreamRhythm:582`,
   `persistDialogueOutcomeAndLearn:640`). Six modules on the list run on every live conversational turn.
   A turn-reachability claim anchored only on `production-turn-runtime.ts` cannot see either lane.
3. **Storage ports cross the boundary as types, not imports.** `storage.ts` reaches
   `brain-lifecycle.ts`, `segmentation-aggregate.ts` and `language-induction-persistence.ts` only through inline
   `import("./x.js").T` type positions (storage.ts:861-864, 1113, 1120). Their *data* reaches the turn through
   `deps.storage.*`; their *code* does not run in a turn. Both halves of that are true and the import walk shows
   neither.

Checked and ruled out: no dynamic `await import(` exists anywhere on the turn path (the only `import(` hits in
kernel src are type positions and one string literal in `program-runtime.ts`). The DELIBERATELY_UNWIRED registry
in `tools/runtime-reachability.mjs` is symbol-scoped, not module-scoped; exactly one of the 67 is covered by it
(`multilingual-alignment.ts`, via `createAlignmentEngine` and `clusterLanguageProfiles`).

## Bucket A, ranked, with the smallest honest change

1. **cognitive-capability-manifest.ts** — the module that exists to make inactive cognition impossible to mistake
   for active cognition has no caller. `learnedCapabilityStatus` (the untrained/fitted/validated/promoted ladder)
   and `buildCognitiveCapabilityManifest` (which computes `observationalBlindSpots` and `inert`) are exported from
   the barrel and called by nothing. The relation-potential failure has a designed remedy in the tree and the
   remedy is unreachable. Smallest change: each learned component on the turn path reports its artifact state
   through `learnedCapabilityStatus`, and `turn.output` carries the manifest beside `support.timing`. It is
   read-only and adds no per-turn DB work, but it spans one call site per learned component, so it is small per
   site and not a one-liner overall.
2. **sparse-ranking-calibration.ts** — `sparse-ranking.ts:259` accepts an optional fitted Platt calibration and
   `:297` falls back to the raw sigmoid without it; `fitFtrlCalibration` is the only producer and has no caller.
   The turn already logs the inputs a fit needs (`production-turn-runtime.ts:2011-2032` writes
   `deps.sparseRankingComparisons` fire-and-forget), so examples accumulate for a fit that never runs. The read
   side does not exist: `sparse-ranking-lifecycle.ts` contains no mention of a calibration, so the persisted model
   record cannot carry one. Smallest honest change is three-sided — extend the model store record, fit in the
   existing post-turn fire-and-forget lane, read it back where the ranker is built — and it must report
   `inert_unconfigured` until a fit is promoted. Not a small change; it needs a store/schema change, which is
   why I did not attempt it here.
3. **construction-grammar-selection.ts** — selection over learned constructions, reachable only from the training
   batch. Wiring it at realization would report `inert_unconfigured` today (no promoted construction artifact from
   this corpus), which is the honest state, not a defect. Smallest change: mouth's realization lane calls it and
   records the status; do not let it silently return identity.
4. **detail-signal-adapter.ts** — `detailProfileIdFromSignal` maps a signal to a control-plane detail profile, and
   `control-plane-profiles.ts` is already turn-reachable while this adapter is not. Smallest change: the turn's
   control-plane decision derives its profile through this function instead of wherever it currently does.
   Lowest value of the four — verify the turn actually has a detail signal to map before wiring it.

## What I implemented

Nothing. The budget went to classification, and the two highest-value A items are both multi-site changes: the
manifest needs one call site per learned component to be worth anything, and the FTRL calibration needs a store
record it does not have. Wiring either half-way would produce exactly the shape this task exists to prevent — a
component that looks wired and reports success while contributing nothing. The ranked list above is the honest
deliverable.
