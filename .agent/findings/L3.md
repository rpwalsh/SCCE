# L3 -- the 40 cloze rows that declined when the answer was in the corpus

Baseline: `artifacts/head-to-head/results-baseline-20260913.json`, workload `cloze`, 160 rows,
**112 correct / 40 declined_when_answerable / 8 wrong**.

## What actually wins cloze, measured

Every one of the 160 cloze turns was traced (`.scce/traces/2026-09-13T06-48-09-467Z-*.jsonl`) and correlated with
its baseline verdict. One stage separates the two classes perfectly:

| | correct | declined | wrong |
| --- | ---: | ---: | ---: |
| `graph.resolve.near_duplicate_fast_path` fired | **112 of 112** | 5 of 40 | 4 of 8 |
| `candidate.proposal.quotation_recall` fired | 112 | 5 | 4 |

The cloze workload is won entirely by the near-duplicate fast path
(`runtime-graph-retrieval.ts:421`) and the quotation-recall proposer it feeds. It fires when an anchored-retrieval
result contains a near-duplicate of a request sentence. **It never fires for a span retrieval did not return**, so
every one of the 35 remaining declines is a retrieval miss, not an admission or mouth miss.

Admission is not the defect: `sourceIdentityAdmissibleEvidenceForRequest`
(`local-evidence-runtime.ts:2426`) already returns near-duplicate spans ahead of every other tier. It had nothing
to prefer.

## Three things that looked like the cause and are not

1. **"evidence 0 means nothing was retrieved."** 37 of the 40 rows show `evidence: 0`. That field is an artefact
   of the harness: `run.mjs` returns `{ answer: "", ms }` with no `evidence` key on HTTP 422, and 36 of the 40
   declines are 422 `runtime declined: no admissible answer surface`. The turns ran the full pipeline and
   retrieved 155-512 spans each. The evidence-0 / evidence-1 split the task packet suggested does not exist.
2. **"the cloze instruction prefix pollutes the anchors."** It does -- `anchor:sym:answering`,
   `anchor:sym:sentence`, `anchor:bi:source|documents` are searched as subjects and `droppedScaffoldingGroups` is
   0 because `requestClosedClassWords` only applies the corpus closed class to a request's first two words. But
   asking the live server the same four rows with the prefix stripped still declined 3 of 4, and the 112 correct
   rows carry exactly the same scaffolding groups. Not the cause.
3. **"the wrong language models are hydrated."** 24 of the 40 declines hydrate 5-8 models including `oss_code`
   ones, and their closed class degenerates to single characters, while all 112 correct rows hydrate 2 Wikipedia
   models. That is a consequence, not a cause: `runtime.seed.language` reports 8 models for **all 160** rows, and
   the 2-model figure comes from `mouth.deterministic.select`, which re-hydrates from the language of the evidence
   actually selected. Rows that selected nothing fall back to the whole set. I believed this for a while; the
   per-stage counts falsify it.

## The cause: the opening-block prior outranks the relevance score

`packages/adapters-node/src/postgres.ts`, the anchor-posting BM25 search, ordered:

    ORDER BY title_exact DESC, title_match DESC, opening_block DESC, hits.score DESC, ...

`opening_block` is `evidence.char_start = 0`. Placed above `score`, it is not a tie-break -- **every candidate at a
document's opening beats every candidate deeper in its document, whatever BM25 says.** It arrived with no comment
in 5f514bc, inside an unrelated commit about language identity.

Measured against the live corpus for `sealed:q-cloze-doc-ada-lovelace-004`, whose answering span is
`ada lovelace @ 12278` and carries **17 of the request's 18 adjacent bigrams**:

| query | rows | of which document openings | rank of the answering span |
| --- | ---: | ---: | ---: |
| `anchor:bi:became|fascinated` alone | 17 | 8 | 10 |
| all 17 carried bigrams | 64 | **64** | **absent** |
| all 17, opening-block prior off | 64 | 13 | **2** |

Adding the 16 features that identify the span made it disappear, because more features admit more candidates and
every additional document opening displaced it. This is the shape that hides forever behind plausible results: the
turn retrieves 200 spans of the right general kind, admission refuses them correctly, and the system declines over
a corpus that holds the sentence verbatim.

Second defect in the same path. The one group that exists for near-duplicate recall took **the four
longest-SPELLED** of the request's adjacent bigrams (`.map(f => ({ feature: f, weight: f.length })).sort(...)`),
so string length stood in for rarity and the conjunction that identifies one span was thrown away. It also
excluded pairs already searched by another group, which breaks the conjunction further, and
`anchorGroupTitleUnits` read a title out of its leading pair -- the quoted sentence's first two words.

## The grouping of the 40

Every one of the 40 answering sentences is present in a span of the ingested corpus (39 in a `promoted` span; for
`ada-lovelace-023` only a quarantined opening block matched, its promoted chunk splits the sentence). Replaying
each row's own traced anchor groups against the live index:

| | n |
| --- | ---: |
| answering span inside the 32 rows a group kept -- retrieved, lost downstream | 20 |
| answering span returned by the SQL but past `usable()`'s `.slice(0, 32)` | 8 |
| answering span never returned by any group's 64 rows | 11 |
| no promoted span carries the sentence | 1 |

## The fix

Two commits, both gated on one structural fact -- `requestSentenceSequences(text).length > 0`, "this request
carries someone else's sentence".

- **73f94b6** `The opening-block prior is not evidence about a quoted sentence`. `EvidenceQuery.openingBlockPrior`
  (default true) and a pure `evidenceRankOrder` that omits the key when it is false; the anchored search turns it
  off for a sentence-quoting request. Regression check:
  `packages/adapters-node/src/__tests__/postgres-evidence-rank-order.test.ts`.
- **e598707** `A quoted sentence is searched as a sequence, not as four long pairs`. The near-duplicate group now
  carries the quoted sentence's adjacent bigrams whole, is not deduplicated against the subject groups, and reads
  no title out of its leading pair.

Retrieval counterfactual over the 40 rows, both changes, against the live index:

| extras group | answering span retrieved | ranked first | in the kept 32 |
| --- | ---: | ---: | ---: |
| four longest-spelled pairs (before) | 31 of 39 | 20 | 31 |
| the sentence's pairs whole (after) | **39 of 39** | **35** | **39** |

## Cost, and where the query width came from

Searching the sentence whole is correct and unaffordable: **p50 10.7s, max 26.4s per query**, against 237ms for
the four pairs it replaces, because every selective feature seeds and a common pair seeds thousands of candidates
the score then ranks. A cloze turn holds eight groups and already runs 30s, and a turn whose deadline elapses
makes the mouth refuse to speak -- the exact failure this change exists to remove.

Pairs are therefore ordered by the corpus's own unigram counts, rarest first (a pair occurs only where both units
do, so the rarer unit bounds its postings), and the query seeds on a declared number of them. Swept against the
live index over the 39 rows whose answering span exists:

| pairs | found | ranked first | query p50 | query max |
| ---: | ---: | ---: | ---: | ---: |
| 6 | 37 | 27 | 17ms | 317ms |
| **10** | **38** | **33** | **73ms** | **785ms** |
| 14 | 39 | 33 | 405ms | 12022ms |
| 20 | 39 | 35 | 2419ms | 17975ms |

Declared as `retrieval.quoted_sentence_query_features = 10` in `public-calibrations.ts` with its search space, not
written inline: it bounds cost AND decides what is reachable, which makes it a modelling parameter rather than a
scan limit. 10 over 14 because the one extra row 14 finds costs a 12-second worst case.

## End-to-end offline prediction

Running the implemented group (rarest 10 pairs, no title read from the leading pair, opening-block prior off)
against the live index, keeping the 32 rows `usable()` keeps, and applying the real
`spanContainsRequestNearDuplicateSentence` to them:

    the near-duplicate fast path would fire on 33 of the 40 rows, against 5 today

Run again over the 112 rows that already pass, as the regression check that matters -- 13 of them are answered by
a span at char_start 0, exactly the ones the opening-block prior was protecting:

    the fast path still fires on 112 of 112

**Why the seven stay silent, and it is one cause.** `requestSentenceSequences` splits the request into sentences,
and the cloze instruction ends in a colon, which `splitSurfaceSentences` does not treat as a sentence end. So the
instruction and the quoted sentence are ONE sequence, and the near-duplicate test needs the corpus sentence to
cover half of its adjacent pairs. For these seven the quoted body is 5-9 units against a whole sequence of 16-20,
so the instruction is more than half the denominator and no corpus sentence can reach the floor whatever
retrieval does:

    ada-lovelace-006  body 6 of 17    star-trek-038  body 8 of 19    tos-011  body 7 of 18
    ada-lovelace-009  body 5 of 16    ds9-035        body 9 of 20    tos-017  body 8 of 19
    star-trek-016     body 9 of 20

Each body alone is a valid sequence (>= 4 units), so separating the instruction from the quoted sentence would
very likely recover them. Not attempted here: it is a change to sentence segmentation, it needs its own
measurement, and it is not what stopped the other 33.

## Containment

Both changes are inert unless `requestSentenceSequences` returns a sequence, and it returns none for any text
ending in a question mark. Measured over the whole 311-row suite:

    workload        n    interrogative   non-interrogative
    cloze         160         0               160
    abstention     59        59                 0
    factual        50        50                 0
    abstention/book/relation/code/direct: 133 prompts, 133 interrogative

So no graded row outside cloze can take either changed path. The abstention workload is still run live as the
control, because a containment argument that holds in the code can still be wrong about which prompts take which
path.

## Directness: the answer contained the fact, it did not state it

Measured with `tools/answer-directness.mjs` on the frozen run: SCCE answers 149 correct and reaches the fact
inside the first 60 characters on 55 of them. **Cloze is 112 correct and 41 direct -- 71 of the whole suite's 94
buried answers.** The shape is one shape: the prompt gives a sentence with a hole and asks for the missing text,
and the answer is the whole completed sentence, so the value sits behind a replay of the request's own words.

The hole is recoverable with no language knowledge, because the near-duplicate path has already established that
the request and the surface are the same sentence. Align the two by longest common subsequence over Unicode
letter/number runs; the longest maximal run of surface tokens outside the alignment is the hole; slice it out of
the surface by the character offsets of its first and last token. `packages/kernel/src/quoted-gap.ts`.

It is silent unless it is certain, and there are four ways to be uncertain, each falling back to the sentence:

- the surface is not exactly the quotation with ONE run missing (`matched + gap !== tokens`)
- two runs tie for longest, so which one is the hole is undecided
- the hole is not smaller than the quotation around it
- the run is not a surface this mouth would speak (`isDegenerateBareSurface` refuses a two-character cased unit,
  and an empty answer is a decline)

Measured over the 112 cloze rows the frozen run scored correct, with the grader's own rule and no row re-judged:

| | n |
| --- | ---: |
| run recovered | 111 |
| run alone still satisfies the grader | **111 of 111** |
| run is a degenerate surface | 0 |
| fact inside the first 60 characters, today | 41 |
| fact inside the first 60 characters, with the run | **111** |

**Why it emits the run alone rather than ahead of the sentence.** Prefixing is verdict-safe by construction and
was the obvious choice. It is the wrong one. The excerpt governance at `production-turn-runtime.ts:4195`
substitutes the deterministic surface for a non-excerpt learned surface only when
`stitched = learnedNotAnExcerpt && isContiguousExcerpt(sourceBound)`. A deterministic surface welded from two
places cannot satisfy that: it would not be rejected loudly, it would silently stop rescuing those turns and leave
the bad learned surface standing. A run of the surface is a run of the span, so the governance sees what it saw
before.

The `TrekMovie` / `TrekMovie.com` failure of the earlier attempt at `:4185` does not reproduce and has a test:
those boundaries came from learned units, these come from where the request stops accounting for the surface, and
the run is sliced by offset rather than rejoined from tokens.

## Not mine, found on the way

- `spanContainsRequestNearDuplicateSentence` (`local-evidence-runtime.ts:2553`) reads only the first 12,000
  characters of a span, or 4,000 when the span is over 6,000 characters and not boundary-joined. That is the same
  truncation pattern L4 removed from `spanCarriesAnsweringSentence`, in the same file, and it gates the single
  test the cloze workload is won by. It does not reach these 40 rows -- every answering span here is a
  ~4,096-character Wikipedia chunk -- but it would silently hide a quoted sentence in a book-length span.
- `requestClosedClassWords` applies the corpus closed class only to a request's first two words, so no
  multi-word instruction frame is ever recognised as scaffolding. `droppedScaffoldingGroups` is 0 on all 160
  cloze rows while `anchor:sym:answering` and `anchor:sym:sentence` are searched as subjects. Costs query budget
  on every row; not the cause of any decline measured here.
- The 8 `wrong` cloze rows are two shapes: 4 echo the prompt sentence without filling the blank (the gold is a
  section heading the prompt blanked out), 4 emit `generation construction inventory from the retrieval corpus`
  followed by a bag of request words. Neither is a retrieval defect. Untouched.
- `sealed:q-cloze-doc-star-trek-tos-040` is graded `declined_when_answerable` while its answer is a full
  sentence: `grade.mjs`'s `declines()` matches the substring `unknown` inside "largely unknown actors".
