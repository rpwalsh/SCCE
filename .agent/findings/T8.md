### Assertion that does NOT catch a regression

In "does not name a run that is merely contained in a longer identity", the second half primes the long
title and asks about "explain relativity". That direction is structurally impossible in the current design
-- matching runs from identity to request, never request to identity -- so no revert I could apply makes it
fail. It is documentation of the invariant, not a regression catcher. The first half of the same test is
what fails under R1.

## 2. Cache entry sizing -- packages/kernel/src/__tests__/surface-language-cache-sizing.test.ts

The entry weight is private to the runtime closure, so the test observes it the way the defect was observed
live: whether two entries can be resident at once under one byte bound. The fixture hydrates ~8KB of records
while deliberately retaining 16MB of heap inside the hydration, under a 512KB cache bound.

### B1 -- heap delta allowed to override the content estimate

`approxEstimatedBytes: approximateHydrationEstimatedBytes(hydrated)` becomes
`Math.max(approximateHydrationEstimatedBytes(hydrated), hydrated.measuredHeapBytes ?? 0)`

```
 ❯ surface-language-cache-sizing.test.ts (2 tests | 1 failed)
   × weighs an entry by the records it holds, not by the heap measured while it hydrated
     → hydrated runtime unavailable: resident language-memory:language-scoped was not warmed

Error: hydrated runtime unavailable: resident language-memory:language-scoped was not warmed
 ❯ residentRuntimeNotWarm packages/kernel/src/surface-language-runtime.ts:803:11
 ❯ Object.hydrateSurfaceLanguageMemoryCached packages/kernel/src/surface-language-runtime.ts:675:49
 ❯ surface-language-cache-sizing.test.ts:24:24
```

That is the live symptom exactly: 70MB of records charged as gigabytes, so nothing can be cached beside
anything else and the older entry is evicted by the newer one.

### B2 -- single flight removed

The in-flight map is dropped and the hydration awaited directly.

```
   × hydrates one language key once for concurrent requests and hands both the same result
     → expected 2 to be 1

AssertionError: expected 2 to be 1
 ❯ surface-language-cache-sizing.test.ts:46:32
    46|     expect(fixture.hydrations).toBe(1);
```

The fake hydrator counts its calls and blocks on a gate the test opens, so both requests are provably
in flight at once.

Restored, both pass:


### Assertions that do NOT catch a regression

Two assertions inside the sizing test pass under both behaviours and are there to keep the test honest
rather than to catch anything: `hydrations === 2` (the two entries really were hydrated separately), and
the second arrangement where 4000 records overflow the same bound with no measured heap at all (content
exceeds the bound either way, so heap-based sizing evicts too). The catching assertion is the first one.

## Pre-existing failures found at e0ae566, NOT caused by these tests and NOT touched

Both were already failing before anything here was written, and both are caused by cd2b507.

### packages/kernel/src/__tests__/surface-language-runtime.test.ts -- 2 of 7 fail

```
   × reuses expired warmed language, frame, and source-profile entries without durable calls
     → hydrated runtime unavailable: resident language-memory:source-surface-ambiguous-or-no-signal was not warmed
   × evicts the oldest entry instead of growing without bound once the request-text-keyed caches exceed their configured size
     → expected 6 to be 4
```

Cause: `hydrationWorthCaching` (new in cd2b507) stores only hydrations carrying at least one model, and that
fixture's `listNgramModels` returns `[]`, so nothing is cached at all and every lookup is a durable miss.
Confirmed by temporarily making the predicate return true: 7 of 7 pass. The new gate looks right and the
fixture is the stale part, but fixing a test fixture is a change to an existing test, so it was left alone
and is reported instead. The new sizing test supplies observations so its hydrations carry a real model.

### packages/kernel/src/__tests__/runtime-deadline-turn.test.ts -- 2 of 2 fail

```
   × still returns a real answer when the production deadline metadata has already elapsed
     → expected 0 to be greater than 0
   × produces the same kind of real answer when the deadline has not elapsed, as a control
     → expected 0 to be greater than 0
```

Cause: the prompt-echo gate. Those tests assert `result.answer.trim().length > 0` for
"Zephyr valve pressure stabilizes after calibration." on an empty corpus, and the "real answer" they were
passing on all along was that sentence echoed back. The gate now refuses it, so the answer is empty. This
is the gate working, and the same behaviour the new echo test locks in from the other side; the deadline
test's own premise (an empty corpus can produce a real answer) is what is now false. Not weakened, not
touched -- it needs a fixture that can actually answer, which is a separate change.
