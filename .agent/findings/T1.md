## Measured runtime facts behind the command choice

- `node --check <file.mjs>` is a real syntax gate: exit 1 with `SyntaxError: Unexpected end of input` on an
  unbalanced brace, exit 0 on a valid module.
- `node --check <file.ts>` is a no-op here: it exited 0 on a file with an unbalanced brace. A `.ts` build step
  would have been a fake gate, so the emitted artifacts are `.mjs`.
- `node <file.mjs>` runs and propagates a non-zero exit from `node:assert`.

## Remaining uncertainty, stated plainly

1. **The declared symbol's behaviour is not synthesized.** The emitted module carries
   `uniqueStrings(values: string[]): string[]` as a checked contract with a sample call; it does not contain a
   function that returns unique strings in first-seen order. Nothing in this engine can derive "unique, in
   first-seen order" from prose without the request-to-code lane (`code-intent.ts` documentation retrieval plus
   `code-construction.ts` composition over trained corpus models), which needs the database and trained models and
   is therefore out of an offline emitter's reach. Lifting a definition out of an evidence span was considered and
   rejected: the corpus is TypeScript, the emitted runtime loads JavaScript, and a partial type-stripper would have
   broken the build on exactly the live path that currently fails. Emitting a function named `uniqueStrings` whose
   body is not that operation would be worse than emitting none, so none is emitted. This is the honest boundary
   of T1 and the natural next task.
2. **The observed-toolchain branch is untouched and probably still cannot build.** When the corpus does supply a
   package manager, the commands stay `pnpm run build` / `pnpm run test`, which cannot succeed in an ephemeral
   workspace with no `node_modules`. Two tests pin that behaviour, the live turn observed in T1's evidence took the
   no-toolchain branch, and changing it was out of scope. If a live coding turn ever resolves a pnpm profile it
   will fail there instead.
3. **The plan's capability choice for this request is wrong, and was already wrong.** `structuralSignals` reads the
   three commas in the acceptance request as a delimiter and selects `capability:validated-transform`
   ("source-derived data flow"), which is why `requiredFields` comes back as symbols scraped from evidence
   (`uniqueStrings`, `Set`, `for`, `if`, `seen`, `out`). The emitted program runs and is tested regardless. Profile
   selection is a separate defect.
4. **Not verified live.** No server was started and no live gate was run, per the task's constraint. The offline
   harness covers acceptance chain A's build/test and chain B's repair loop against the real adapter, but the live
   `tools/coding-spine-acceptance.mjs` run belongs to the integrator.
5. **Two pre-existing failures observed, neither caused by this change, both proven so.**
   `cognitive-planner.test.ts` "constructs algorithm and architecture designs only from program structure..." fails
   identically with `program-planner.ts` and `code-learning.ts` restored to cd2b507 (1 failed, 13 passed); its
   fixture is a literal `ProgramGraph` and `cognitive-planner.ts` imports neither changed module.
   `tools/no-hidden-model-check.mjs` exits 1 naming `tools/head-to-head/run.mjs` and
   `tools/reference-comparison-large.mjs`, both untouched here.
