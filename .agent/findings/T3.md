## Result

There is no 5.2 s of pre-kernel work. The premise reads `remainingMs` against an assumed 10 s window; in the
run that produced the quoted 4839 the kernel's window was 5000 ms, and the same event records that only
161 ms had elapsed. Measured pre-kernel time across every trace on disk is p50 51 ms, p90 200 ms.

## The quoted turn, measured

`2026-09-13T03-54-03-292Z-trace_mtza4zvg_oxpsrf.jsonl`, event 364. Its own `durationMs` is
`observedAtMonotonicMs - deadlineMetadata.startedMonotonicMs` (production-turn-runtime.ts:790), so it *is* the
pre-kernel elapsed time:

```
event 364  runtime.deadline.check [kernel.turn.start]  durationMs=161.286  remainingMs=4838.714
161.286 + 4838.714 = 5000.000
```

Every turn in that run sums to exactly 5000.000, while the server's own `turn.deadline.observed` for the same

All 103 `kernel.turn.start` events in the whole trace directory whose `remainingMs` lands in [4700, 4990] come

"5.2 s elapsed".

## The clock is not mis-stamped

`requestTiming.startedMonotonicMs = performance.now()` is the first statement of `handleRequest`
(routes.ts:178), before auth, body read and dispatch. Checked against wall clock two ways per turn: the
kernel's stamp recovered as `wall(kernel.turn.start) - durationMs`, and the server's as
`wall(turn.deadline.observed) - elapsedMs`, both compared to the `api.request` event:

```
run 2026-09-13T03-54-03 (7 turns)   kernelStartOffset -0.4 .. +0.3 ms   serverStartOffset -4.4 .. +6.2 ms
run 2026-09-13T04-16-11 (12 turns)  kernelStartOffset -0.8 .. +0.5 ms   serverStartOffset -0.8 .. +0.6 ms
```

Both stamps land on request arrival, within a millisecond. There is no earlier stamp and no non-turn work
inside the clock. Moving the stamp would not recover time; there is no time there to recover.

## Where the pre-kernel milliseconds actually go

Three measurable sub-intervals between the clock start and `kernel.turn.start`:

| item | what it is | measured |
| --- | --- | --- |
| arrival to readiness start | auth, route match, `readBody`, `validateTurn`, deadline creation | 0-8 ms typical, one 412 ms outlier in 1753 turns |
| `turn.runtime.readiness` | the `Promise.all` at routes.ts:700 -- surface-language check, `listTurns`, hydrated-runtime marker, dialogue style/outcome/pragmatics reads | p50 47, p90 188 ms; 97-99% of pre-kernel |
| readiness to kernel entry | discourse object, metadata assembly, kernel call | 1-45 ms |

The tail is not per-request work. Two causes, both visible in traces:

- hydrated-runtime cache miss. `turn.runtime.readiness` with `source: durable_verification` instead of
  `startup_verified_cache` costs seconds (7877 ms, `2026-09-10T08-43-25`). Process warmup charged to whichever
  turn arrives during it.
- another turn still computing. In `2026-09-10T10-22-14` event 1501 the previous turn's
  `mouth.deterministic.select`, `runtime.validation.complete`, `turn.output` and `turn.calibration.loaded`
  events all land *inside* the new request's readiness window; readiness reads 2824 ms of which the new turn
  did none. Node serializes them; the clock, correctly started at arrival, is charged for the queue.

## What the budget is actually spent on

In the newest run on disk (`2026-09-13T04-16-11`, window 10000.000 on all 12 turns, pre-kernel 7.5-707 ms,
median 85 ms), the budget goes downstream of the kernel entry, not before it:

```
turn 1     52ms kernel.turn.start                 rem=9948 admitted
         6695ms runtime.seed.language.complete    rem=3305 admitted
        17563ms retrieval.learned-semantics       rem=   0 response_deadline_elapsed
turn 3     86ms kernel.turn.start                 rem=9914 admitted
          238ms runtime.seed.language.complete    rem=9762 admitted     (warm: 0.2 s, not 6.7 s)
         9167ms retrieval.learned-semantics       rem= 833 compute_reserve_exhausted
```

Cold turns lose the budget to the language seed; warm turns lose it to the graph slice / retrieval
(`graphSliceMs: 8718` on turn 3). Both are kernel-side and out of T3's scope.

## Change made

A precise attribution was the deliverable, and the largest item -- a 5000 ms window from a build state that is
no longer on disk -- is not something I can safely change. What I did change is the instrument that allowed a
161 ms measurement to be read as 5.2 s:

- `packages/kernel/src/production-turn-runtime.ts`: the deadline-check trace now records `budgetMs`, the window
  its `remainingMs` counts down from. One field, no behavior change, no constant touched.
- `tools/pre-kernel-latency.mjs`: offline harness, no server and no database. Reports the pre-kernel
  distribution and flags any turn whose kernel window disagrees with the server's reported budget -- the exact
  divergence that produced this task.
- `packages/kernel/src/__tests__/runtime-deadline-turn.test.ts`: regression check. Fails without the fix with
  `expected undefined to be 5000`.

Nothing weakened, no deadline raised, no test bar lowered.

## Remaining uncertainty

- The two older tests in `runtime-deadline-turn.test.ts` are already red at `cd2b507` (`expected 0 to be
  greater than 0`, empty answer). Verified pre-existing by running them against main's own copy of
  `production-turn-runtime.ts`. Not touched, not in scope, reported.
- I could not identify the build that emitted the 5000 / 9750 / 9900 ms windows. Current source cannot produce
  one: routes.ts writes `budgetMs: 10000` with `deadlineMonotonicMs = started + 10000`, and
  `runtimeDeadlineMetadataFromJson` rejects any row where `|deadline - started - budget| > 1`. The compiled
  `packages/server/dist/routes.js` on disk (built before those runs) also carries 10000. That build state is
  gone. The new `budgetMs` field and the harness's disagreement check will name it immediately if it returns.
- No trace on disk postdates the current baseline: newest is `2026-09-13T04:16Z`, `cd2b507` was committed
  `2026-09-13T04:49Z`. The post-baseline build is not directly measured. I did not start, restart or call the
  server.
