# T11b — how to persist and load a globally induced lexical-family graph

base: `e0a9171` · design only, no production code touched, no DDL run.

Answers one question: **how is a globally induced family graph persisted and loaded per turn so a turn does
not need every family member present in its own hydration slice?** It does not test morphology and takes no
position on whether the syntactic factor works; it assumes it might and sizes for it.

## 1. The constraint restated as an engineering problem

T10 measured that `grind`, `wound`, `kound` and `borna` are absent from the 20,598 types a turn hydrates, against
317,571 in the full corpus. The hydration slice is not a sample of the corpus, it is a **cluster-scoped** slice:
`hydrateSurfaceLanguageMemory` loads n-gram models for the profiles of the request's language cluster under a
48 MB JSON byte budget (`SCCE_LANGUAGE_HYDRATE_NGRAM_MB`, default 48). Any per-type evidence stored inside that
slice is therefore *definitionally* unavailable for a type the slice did not select. No amount of budget raising
fixes it — the budget is a memory bound, and the eviction it protects is real (measured: 120 MB of JSON hydrates
to 3.3 GB of heap).

So the family graph cannot live in the hydration. It must be **corpus-global, process-resident, and independent
of which cluster the turn selected.**

### Size of the graph at the proposed shape

Three components. Only the third is large.

1. **Surface dictionary** — 317,571 types × (7.064 chars + ~3 B JSON quoting/comma) ≈ **3.2 MB** of JSON.
2. **Accepted transformations** — T10 induced 33,926 transformations over 20,598 types and MDL+null accepted
   **1,771** (1,522 with both sides non-empty). Scaling the accepted count linearly in V to 317,571 types gives
   **≈ 23,500** accepted transformations — a deliberate over-estimate, because MDL acceptance needs population
   support and the accepted set concentrates sub-linearly while the *induced* set grows roughly linearly. The
   induced set (≈ 520,000 at that scaling) is an offline intermediate and is **never persisted**. Record =
   `{lc, from, to, rc, eligible, members, logBF, gainBits}`; the admission rule bounds `|from|+|to| <= p+s` so the
   strings are short. ≈ 90 B each → **≈ 2.1 MB**.
3. **Memberships** — (surface → family) edges with the member's own counts. A type sits on the from- or to-side
   of a small number of families; at k = 2 average, 317,571 × 2 ≈ **635,000 edges**. As naive JSON
   `["grind",412,15]` ≈ 20 B → **12.7 MB**; as two parallel integer arrays against the dictionary (12 B/edge)
   → **7.6 MB**.

**Total: ≈ 18 MB of JSON, ≈ 13 MB packed.** On disk as JSONB with TOAST compression, expect 8–12 MB — one row,
about ten times `model_state.default` and **0.3 %** of `language_patterns.pattern_json`.

Resident heap, held once per process (not per cache key): 317,571 interned strings ≈ 17 MB + 635k edges in
`Int32Array` pairs ≈ 5 MB + 23.5k family records ≈ 5 MB → **≈ 30 MB**, i.e. 0.4 % of the 7 GB heap and smaller
than one hydration's 48 MB n-gram budget.

## 3. Chosen persistence shape, and why not the other eight

**One row per induction run in a new table `lexical_family_models`, shaped exactly like
`segmentation_population_models`:**

```
lexical_family_models(
  id TEXT PRIMARY KEY,
  training_plan_id TEXT NOT NULL,
  model_json JSONB NOT NULL,          -- dictionary + transformations + memberships
  population_count INTEGER NOT NULL,  -- distinct types the induction saw
  family_count INTEGER NOT NULL,
  mdl_gain_nats DOUBLE PRECISION NOT NULL,
  corpus_watermark JSONB NOT NULL,    -- {sourceVersions, newestObservedAt} at induction time
  information_label JSONB NOT NULL,
  created_at TIMESTAMPTZ NOT NULL)
CREATE INDEX ... ON lexical_family_models(created_at DESC)
```

Why this and not a ninth shape: the schema already has a template for *"globally induced, MDL-scored artifact,
one row, JSONB payload, newest-first"* — `segmentation_population_models` carries `model_json`, `population_count`
and `mdl_gain_nats`, which is the same triple a family graph needs, and its sibling `induced_language_models`
carries `vocabulary_size` for the same reason. Copying it costs nothing and inherits the writer conventions in
`packages/kernel/src/language-induction.ts`.

Why the others are wrong:

- **`language_patterns`** (48,832 rows / 4.4 GB) is the obvious-looking home and is the trap. It is keyed by
  `profile_id` and hydrated *inside* the 32 MB `languagePatternJsonBytes` budget of the cluster-scoped hydration.
  Putting families there reintroduces exactly the slice problem T11 exists to escape, and makes families compete
  for budget with the patterns a turn already needs.
- **`language_units`** is per-unit, per-profile, 452,317 rows — a family edge table there would be a second
  per-turn scan and is again profile-scoped.
- **`ngram_models`** is the slice.
- **`model_state`** is the closest *behavioural* precedent (single global row, `SELECT model_json ... WHERE
  id='default'`, PK lookup, 1.17 MB, populated) but it is an undifferentiated bag with no versioning, no
  watermark and no MDL columns; a 10 MB payload inside it would be re-read by every consumer of `default`.
- **`calibration_observations`** is an append-only observation log, not a fitted artifact.
- **`sparse_ranking_models`** is the right *lifecycle* idea (lifecycle column, active-model pointer, rollback
  reason) and is worth copying **if** families ever need A/B rollback. It is 1 row in production; adopt its
  `previous_active_model_id`/`rollback_reason` columns only when a second induction run exists to roll back to.
- **`language_identities`** is 9 rows of JSONB and is the *anti*-precedent (see §6).

**Skeptic note, load-bearing:** `segmentation_population_models` and `induced_language_models` both contain
**0 rows**. The read path is genuinely wired — `hydrateSurfaceLanguageMemory` fetches
`segmentationPopulationModels` inside its `Promise.all`, so it runs on every durable hydration — but it has never
returned anything in production. The *shape* is precedent; the *pipeline that fills it* is not. A T11
implementation must therefore ship its own offline writer (a CLI subcommand) and prove the row exists, rather
than assuming the induction orchestrator will populate it.

## 4. Load path

**Not** via the hydration. A field on the hydration value would be duplicated per cache key, counted by
`approximateHydrationEstimatedBytes`, evicted with the cluster that happened to trigger it, and re-fetched per
cluster — 30 MB × N entries against a cache whose whole purpose is a byte bound.

Instead, the graph is a **process-global stale-while-revalidate singleton with single-flight**, copied verbatim
from `sourceTitlesCached` in `packages/adapters-node/src/postgres.ts:2265`, which is the fix that replaced the
19.5 s unindexed `DISTINCT` over `evidence_spans`:

- module-level `lexicalFamilyCache = { graph, loadedAt, watermark }` and `lexicalFamilyInFlight`;
- a hit inside `LEXICAL_FAMILY_REFRESH_MS` returns immediately;
- a stale entry **returns the stale graph and refreshes behind it**; a refresh that throws keeps serving what it
  has (`.catch(() => cache?.graph ?? empty)`);
- only the first caller of a cold process ever awaits;
- the graph is *interned once* into `Map<string, FamilyMembership[]>` plus a right-context index, so lookup is
  `O(surfaces in request)`, not `O(families)`.

A turn then asks `familyGraph.membershipsFor(surface)` for each content surface. **`grind` need not be in the
hydration slice**: the turn holds the `i>ou@nd` family's global counts (find/found 2606/6430, bind/bound 69/711,
grind/ground 15/1935, …) because they were induced over all 2,028 models offline and are resident in the
singleton, not in the slice.

The graph is a **likelihood factor, never a gate**. If the row is missing, stale, or still loading, the factor is
absent and selection behaves exactly as it does today. This is T10's measured lesson: composing T6 as a hard
precondition killed `bind/bound`, because `bind` has t=5 in the resident models.

## 5. Per-turn cost, and how to verify it

| state | queries | cost | basis |
| --- | --- | --- | --- |
| warm (turns 2..N) | **0** | **< 1 ms** | hash lookups over ~10 request surfaces; the same shape as the title list, described in-code as "a substring test over ~22k short strings, which is microseconds" |
| stale-refresh turn | 0 blocking | **< 1 ms** | SWR returns the old graph; the refresh runs behind the turn |
| cold process, first caller | 1 | **≈ 100–300 ms once** | `model_state.default` is 1.17 MB and parses in tens of ms; 10 MB scales linearly. Single-flight means exactly one caller pays; and it need not pay at all, because the factor is optional |

This does **not** reintroduce the 19.5 s shape. That cost was an unindexed `DISTINCT` over every `evidence_spans`
row, asked *per request* and cached per request *text*, so every new question paid it in full. Here there is one
PK/`created_at DESC` index lookup of one row per process per 10 minutes, and the result is keyed by nothing at all.

Verification, before shipping:

1. `EXPLAIN (ANALYZE, BUFFERS)` the load query once (`pg_explain`) and require an index scan returning 1 row.
2. Emit a `lexical.family.load` trace event in the shape of `language.cache.lookup`, with
   `{hit, rows, bytes, elapsedMs}`. Run `node tools/conversation-probe.mjs` and require `hit=true, elapsedMs≈0`
   on every turn after the first, and **zero** `lexical.family.*` database events after the cold load.
3. Diff `support.timing` at `turn.output` across the probe before and after; the family phase must not appear as
   a distinguishable phase.
4. Assert resident occupancy via the existing `cacheOccupancy()` accessor plus one `process.memoryUsage()` delta
   at load: require < 64 MB, and require that the surface-language cache's `approxEstimatedBytes` is **unchanged**
   (proof the graph is not inside the hydration entries).

## 6. Staleness — not another one-shot

Language identity discovery is a one-shot: documents ingested after the last `scce language identities --rebuild`
carry **no identity at all**, and nothing says so. Three mechanisms prevent repeating it, two of which already
exist in this codebase:

1. **TTL + SWR + single-flight**, as above. `SOURCE_TITLE_REFRESH_MS = 10 * 60 * 1000` is the working precedent,
   commented "the corpus only changes when something is ingested, so this is refreshed on an interval rather than
   asked per turn". Use the same interval. A stale graph still answers.
2. **A corpus watermark stored in the row.** `corpus_watermark = {sourceVersions: 24735, newestObservedAt:
   '2026-09-12T23:15:59Z'}` — measured above, one cheap aggregate over `source_versions`. The refresh compares
   the live watermark against the row's; if the corpus has not moved, the refresh is a no-op and the 10 MB
   payload is **not** re-read. This is precisely what language identities lack: a way to know it is behind.
3. **Monotone extension between rebuilds.** Because a family is decided by *global population* evidence, a newly
   ingested type that matches an already-accepted transformation can join that family with its own counts without
   re-running MDL. *Accepting a new family* requires a rebuild. So drift is bounded and directional: the graph can
   only become more complete between rebuilds, never wrong. The row carries `unmatched_since_rebuild` (types seen
   at refresh that fit no accepted transformation) as the observable rebuild signal.

And the staleness state must be **reported, not silent**: surface `{familyGraphAgeMs, watermarkDelta,
unmatchedSinceRebuild}` on the readiness endpoint so a stale graph is visible without reading a trace. The
one-shot's real defect was not that it went stale — it was that going stale was invisible.

## 7. What I could not determine

- **The full-corpus accepted-family and membership counts are scaled, not measured.** 23,500 transformations and
  635,000 edges are extrapolations from T10's *measured* resident-scale counts (33,926 induced / 1,771 accepted /
  1,522 two-sided at 20,598 types). Measuring them for real means running the induction over 317,571 types, which
  is the other investigator's lane. The byte figures in §2 are therefore **bounds with a stated basis**, and the
  extrapolation is deliberately generous (linear where the accepted set is sub-linear).
- **V = 317,571 is T10's figure, not re-derived here.** Re-deriving it means detoasting 1.43 GB of `model_json`
  and distinct-sorting ~30 M rows, which would have competed with the benchmark currently running. The mean type
  length (7.064 chars) *is* measured here, over the 25,322 distinct types in the 8 largest models; the true
  corpus-wide mean is likely slightly higher (rare types are longer), so §2's byte figures round up to 8 B/type.
- **Whether the offline induction can produce the graph within a tolerable wall clock** — unmeasured. T10's
  harness enumerated by prefix and first/last-character buckets with a >4000 bucket skip as a cost bound, over
  20,598 types. At 15.4× the vocabulary the bucketing is the thing to re-cost before committing.
- **Whether the syntactic factor separates the 11 members of `i>ou@nd`.** Out of scope by instruction, and the
  design is deliberately indifferent to it: the persisted record carries whatever per-member evidence the
  induction produces, and the load path does not care what the fields mean.

## 8. Migration sketch (not run — DDL on `evidence_spans` is ~15 min/statement and blocks the server)

The new table touches **no existing table**, so it needs no `ALTER` and no index on `evidence_spans`. It is one
`CREATE TABLE IF NOT EXISTS` plus one `CREATE INDEX IF NOT EXISTS` appended to the migration list in
`packages/adapters-node/src/postgres.ts` beside `segmentation_population_models` (line ~999), a store created in
the constructor beside `createSegmentationPopulationModelStore`, and one `latest()` accessor. The writer is an
offline CLI subcommand; nothing on the turn path writes it.
