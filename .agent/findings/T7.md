# T7 — G9 multilingual parity

Verdict: **the close criterion is not met for any of the five identities, and cannot be met by this corpus.**
The naming mechanism is genuinely script-neutral; the corpus it reads is monolingual English. Those are two
different claims and they have opposite answers, so this report scores them apart.

Harness: `tools/multilingual-parity-gate.mjs` (offline; read-only SQL; `--no-db` runs the pure section alone).
All output below is pasted from it or from the read-only probes behind it.

## 5. The mechanism, separately: 10/13 writing systems

Section D primes the arbiter with a synthetic one-title corpus per writing system, so orthography is the only
variable. This is the part of the claim that holds.

| writing system | verdict |
| --- | --- |
| Latin / English, Welsh, Lakota | PASS |
| Cyrillic (nominative) | PASS |
| Han (all-Chinese), Han+Kana (all-Japanese) | PASS |
| Arabic, Hebrew, Devanagari | PASS |
| **Hangul, normal eojeol** | **FAIL** |
| **Han+Kana with one Latin token** | **FAIL** |
| **Cyrillic, inflected** | **FAIL** |

Corroborating the "by construction" half: the naming path carries no hardcoded English word list and no
ASCII-only character class (`grep` over `corpus-identity.ts`, `corpus-identity-runtime.ts`, `language-identity.ts`
for `a-z` returns nothing). Unit splitting is `[^\p{L}\p{M}\p{N}'’-]+`, which reads the same in every script.

### The segmentation defect (one root cause, two failures)

`corpusNamedIdentities` in `packages/kernel/src/corpus-identity.ts` computes the containment fallback **once over
the whole request**:

```js
const unspaced = !surface.trim().includes(" ");
…
return surface.includes(" " + identity + " ") || (unspaced && surface.includes(identity));
```

So containment inside a unit is permitted only when the *entire request* has no space anywhere.

```
  [FAIL] Hangul / normal eojeol
     title   : "서울"        request : "서울의 인구는 얼마입니까?"
     units   : ["서울의","인구는","얼마입니까"]        named : []
  [PASS] Hangul / bare noun
     title   : "서울"        request : "서울 은 어디 입니까"
     units   : ["서울","은","어디","입니까"]           named : ["서울"]
```

Korean writes spaces *between* eojeol but agglutinates particles *onto* the noun, so `unspaced` is false and
`" 서울 "` is never found inside `" 서울의 "`. Korean only works if written the way Korean is not written.

```
  [PASS] Han+Kana / all-Japanese
     request : "日本の首都はどこですか"        named : ["日本"]
  [FAIL] Han+Kana / one Latin token
     request : "日本の首都は Tokyo ですか"     named : []
```

Japanese passes only while the request is pure Japanese. One Latin token — a product name, a loanword, an ASCII
numeral, all ordinary in real Japanese — flips the flag and the subject is lost.

A per-unit test ("allow containment within a unit whose writing system supplies no internal boundary") fixes both
and introduces no casing rule, no suffix list, no word-position rule and no constant. **Not implemented here:**
`corpusNamedIdentities` is on the live turn path shared with other agents, and T7 asked for evidence, not a fix.
Cases exist in the harness and currently fail, so the fix arrives with its regression check already written.

Cyrillic inflection (`Москвы` vs `москва`) is a separate problem needing morphology, which the corpus-identity
arbiter deliberately does not do.

## 8. Where parity holds, and where it does not

**Holds.** The arbiter is script-neutral by construction for Latin, Cyrillic, Han, Arabic, Hebrew and Devanagari:
no casing, no suffix list, no word-position rule, no ASCII class. Given a corpus in those scripts it would work
today. The rewrite achieved what it set out to achieve.

**Does not hold.** (a) There is no non-English source in the corpus, so the close criterion is unreachable — this
is a *corpus* gap, not a code gap, and no amount of engine work closes it. (b) Even with such a corpus, Korean and
spaced-Japanese would still fail on the `unspaced` defect — this *is* a code gap. (c) The five identities are not
five languages, and describing them as such to a reviewer will not survive the first query.

**Recommended wording change.** "Five learned language identities" is true only in the sense that the discovery
algorithm emitted five rows. Claim instead: *the identity-discovery and subject-naming machinery is script-neutral
and learns its closed class from the corpus rather than from a word list; on the present English corpus it resolves
to one prose identity, one code identity, and three degenerate buckets.* That is defensible and still impressive.
The current phrasing is the single most challengeable claim in the set.

## 9. Remaining uncertainty

- Nothing here was verified through a live turn: the server is shared and T7 forbids touching it. The harness
  exercises the corpus identity arbiter end to end (real SQL → built kernel), which is the mechanism the claim
  rests on, but retrieval, ranking and realization downstream of naming are untested for any language.
- The offline access predicate uses the `public` / no-principals / no-compartments slice (50525 of 59669 titled
  spans), because a harness must not forge an `InformationAccessContext`. It is a strict subset of what any live
  requester sees, so it can under-report, never over-report. The code identity's 673 spans are all `public`, so
  nothing in §1 is hidden by this.
- `script:Zxxx` / `script:Zyyy` are read here as ISO 15924 "uncoded" / "Common" against their contents; the
  learned labels come from `learnedScriptIdForCharacter` and were not traced to their derivation.
- Section D's synthetic titles are fixtures, not corpus documents. They prove the mechanism, not the corpus.
- The server package does not typecheck at `e0ae566` (two implicit-`any` errors in `packages/server/src/routes.ts`
  at 3527–3528). Pre-existing on main, unmodified in this worktree, unrelated to T7 — flagged because it is on the
  scored typecheck list.
