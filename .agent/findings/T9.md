# T9 — compute-efficiency proxy

G9's table existed only as a promise. It exists now, built entirely from turn traces already on disk. No server
was started, no turn was issued, no database was written.

A **proxy**, not energy. CPU-seconds are not joules. This host exposes no package-energy counter, so there is no
joules column rather than an estimated one. `packages/kernel/src/resource-usage-accounting.ts` already refuses to
ship a default `PowerModel` for the same reason; this table keeps that refusal.

## Tool

`tools/compute-efficiency-table.mjs` — offline, no server, no database.

```
node tools/compute-efficiency-table.mjs [--traces DIR] [--reference FILE] [--out JSON] [--md MD] [--top N]
```

Outputs `.agent/findings/T9-compute-efficiency.json` (machine-readable, all 220 request groups) and
`.agent/findings/T9-compute-efficiency.md` (the reader's table). `/artifacts/` is gitignored, so the published
copies live under `.agent/findings/` where they can be committed. Recorded paths are repo-relative by
construction: this checkout's directory names never reach the artifact.

## Exactly what each number means

- **wall-seconds** — `process.hrtime.bigint()` differenced around the kernel turn. Attributable to the turn.
- **CPU-seconds** — `process.cpuUsage()` user+system differenced around the same window: every CPU-second the
  **server process** burned while the turn ran. Process-wide, therefore an **upper bound** on the turn's own CPU.
- **peak RSS** — `max(rss at turn start, rss at turn end)`. A process-level high-water of **two samples**: not the
  turn's allocation, not a sampled maximum, and dominated by hydrated state the server holds between turns. It is
  reported because the task asks for it, and labelled so nobody reads it as per-turn memory.
- **GPU-seconds = 0** and **API tokens = 0** — by construction, not by measurement. SCCE's product code loads no
  GPU or model runtime and calls no model API. Basis: `artifacts/no-hidden-model-check.json`, status passed, 1029
  files scanned, `productImportsOfDeclaredReferences: []`, violations none. These two zeroes are the comparison's
  whole point: the reference system's are not zero, and on this host they were never even counted.

Percentiles are nearest-rank, so every published figure is an observation that actually occurred.

## Bounding the CPU attribution error

The task's warning is correct and I did not paper over it. Three things bound it:

1. **Concurrent turns are excluded outright.** A turn is kept only if no other measured turn of the same process
   overlapped its window. 184 of 2652 turns (6.9%) failed this and are dropped from the table, so no other turn's
   work is inside a published CPU figure. They are summarized separately in the JSON.
2. **The residue is bounded by the ratio itself.** Over warm turns the whole process burned **0.984 CPU-seconds
   per wall-second at p50 and 1.684 at p95**. At the median the entire process — background hydration,
   persistence, GC included — stayed under one busy core. The turn's own CPU cannot exceed the published number,
   and the gap available for background work is small.
3. **Background persistence is measurably not the contaminant.** Splitting warm turns by whether a
   `dialogue.persistence.*` event fell inside the window moves the CPU/wall ratio from 0.990 to 0.975 (p50) —
   no separation.

Quantization: this host's process CPU accounting advances in ~15.6 ms steps (the distinct CPU sums are multiples
of it: 32, 47, 63, 93, 109…), so each of user and system carries ~16 ms of error per turn. Negligible against
multi-second turns.

## How warm and cold were separated

Both halves are structural facts read from the trace, not thresholds — no constant decides this.

- **cold** — the first turn a process served, **or** any turn with a `language.hydrate.*` event inside its own
  window. One trace file is one host process: `trace.open` is written when the process opens its trace.
- **warm** — every other turn.
- **scope** — server-hosted processes only (the file carries a `server.start`). 180 turns served by short-lived
  tool processes are counted separately, since "the server is always running" is the condition that matters.

I expected "first turn in the process" to be the cold signal on its own. **The data corrected me**: only 50 of
250 first-in-file turns actually hydrate, and hydration-in-window separates the distributions far better
(p50 19.2 s vs 7.4 s) than position does (11.5 s vs 7.1 s). The rule is the union of the two because each catches
first-time work the other misses.

## Stated before measuring, and how each held

1. CPU-seconds ≈ wall-seconds, single-threaded engine — **held**, ratio p50 0.984.
2. Cold costs materially more than warm — **held**, 14.56 vs 6.17 CPU-s p50.
3. Peak RSS is a large, slowly-growing process number — **held**, p50 3.04 GiB, drifting 3.09→3.92 GB across the
   four days.
4. GPU-seconds and API tokens are 0 for SCCE — **held**, on the dependency gate.
5. No reference CPU/RSS/token figures exist on disk; wall-clock does — **held**.
6. First-turn-in-process is the cold signal — **refuted**, see above.

## What remains unmeasured

- **Joules, for either system.** No package-energy counter on this host. `tools/head-to-head/run.mjs` documents
  the same dead end (`\Power Meter\Power` reads 0, the ACPI thermal zone is empty without elevation) and offers a
  battery-discharge path that only works off AC. Not filled in.
- **Reference CPU-seconds, peak RSS, GPU-seconds and token counts.** Closing this needs one head-to-head run;
  the harness already exists and already samples all four. It is a live-server run, so it belongs to the
  integrator, not to a worktree.
- **Disk I/O.** `captureResourceUsageSnapshot` hardcodes `diskBytesRead`/`diskBytesWritten` to 0, so the
  `diskBytes*` fields in every trace are placeholders. Deliberately not published as zeroes.
- **Build drift.** The corpus spans four days and several builds; warm wall p50 by day runs 6.3 / 8.7 / 4.3 / 5.8
  s. The per-request groups and the day breakdown in the JSON let a reader see it; the headline does not hide it.
