## Left inline deliberately

- **Near-zero guards** in `learned-graph-prior-runtime.ts`: `arc > 0.0001` (641, 1519), `activation <= 0.00001`
  (906, 1415), `topologySupport <= 0.000001` (1171), `affinity <= 0.001` (1820). These are "is this non-zero"
  tolerances, not judgements.
- **Normalizers and scale divisors**: `selected.length / 5`, `importedUseMass / 4`, `selected.length / 4`,
  `model.observedSymbolCount / 10000`, `featureSet(text, 128)`. Structure, not modelling.
- **`0.35` and `0.2` inside the judge risk vector** (`boundaries.length ? 0.35 : 0`,
  `alphaRiskCeiling < 0.5 ? 0.2 : 0`): these are the *magnitude* a boolean contributes, one level below the
  declared vector weight. Declarable, but a second pass — and `< 0.5` there is a conventional midpoint.
- **`endpointSpecificity`'s score ladder** in `graph-edge-quality.ts` (0.9 / 0.82 / 0.68 / 0.6 / 0.45 / 0.52 plus
  `+0.08`, `-0.18`, `-0.16`): a fifteen-value hand-set staircase keyed on symbol lengths. It is one calibration
  object shaped like a curve, not fifteen thresholds, and declaring it piecemeal would misrepresent it. Flagged
  for a dedicated fit; only its `0.34` fragment trigger is declared.
- **Multi-line vectors the inventory tool does not see**: `graph-edge-quality.ts` lines 69–73 (the four-term
  fragment score) and 78–92 (the fourteen-term `semanticQuality` vector, the single most consequential weight
  vector in that file). The tool matches single lines only, so these are invisible to coverage reporting *and*
  were invisible to this task's scope. Worth a follow-up; the tool should learn multi-line expressions.
- **`graph-edge-quality.ts` class quality caps** (`Math.min(semanticQuality, 0.42 / 0.48 / 0.18)`, lines 114–116):
  each class stamps a ceiling on quality. Tuned, undeclared, and not flagged by the inventory.

## Values I believe are wrong (not changed)

1. **`judge.total_*` does not sum to 1 and is not meant to** — `0.32 + 0.24 + 0.2 + 0.12 + 0.12 = 1.0` on the
   positives, then `- 0.42 * risk` and `- telemetryPenalty` (0.72) are subtracted on top. A telemetry-shaped
   answer therefore scores at or below zero on its own, and `clamp01` hides that the penalty is a hard veto
   dressed as a weight. If it is a veto it should be a gate, not a coefficient.
2. **Two explanation-completeness formulas differ only in their numbers** —
   `graph_prior.plan_completeness_*` (0.34/0.24/0.24/0.18) and `graph_prior.realized_completeness_*`
   (0.36/0.22/0.22/0.2) compute the same quantity on the planned and realized routes. Nothing explains the
   divergence; it reads as one being edited and the other not. I declared them separately so a fit can settle it.
3. **`graph_edge_quality.answer_grade_semantic_floor` (0.58) is checked twice** — once inside `answerGradeShape`
   and again immediately after classification. The second check can never fail when the first passed, unless a
   class cap lowered `semanticQuality` in between, which the caps at lines 114–116 can only do for classes that
   are *not* answer-grade. One of the two is dead.
4. **Three distinct scores share the literal 0.55** (`categoryNavigationScore`, `aliasScore`, `titleHintScore`).
   Declared as three ids because they are three decisions; if a fit moves one, the coincidence should not survive.
5. **`graph_prior.weak_fragment_fit_floor` is 0.5** among siblings of 0.62 and 0.64. Declared rather than left
   inline as a "conventional" value, because in context it is a tuned fit boundary and leaving it alone would
   have made the one rejection rule in that block unfittable.

## Search-space entries

Every new id has a `CALIBRATION_SEARCH_SPACE` entry, so the typechecker accepted them. Ranges are honest
brackets around the shipped value (roughly half to 1.6x, clamped), with the shipped value as a coarse point —
they say where a calibrator may look, and no entry encodes a preference for the current number beyond including it.
